Tag and Manifest Entities for OCI Artifacts -- Design

Author: Shreya Baranwal Status: Draft Related issue: #6954

Abstract​

This document defines how Minder represents images in OCI registries so that rules can be applied to them, starting with DockerHub and Quay. Each registered tag is one artifact entity identified by repo:tag, and the digest the tag currently points to is stored in the oci/digest property, so the entity stays the same when the tag moves. Rules get the tag's data through a new oci ingest type, which looks only at the entity's own tag and returns its manifest, platform manifests and requested referrers. Rule authors handle the different OCI index, image and referrer types themselves, including whether a check applies to the index, the platform manifests or both. Repository entities, automatic registration and tag history are left for later.

The identity change landed in #7044; scoping ingestion to the entity's tag is tracked in #7089.

Background​

This design takes the following as given:

  • People want to manage OCI registries through policy.
  • OCI registries think in terms of tags and manifests. A tag is a mutable alias; a manifest is content-addressed and immutable.
  • Zero or more tags can point to a given manifest at the same time.
  • A manifest's digest never changes; the manifest a tag points to can.

State before this design (as shipped in v0.4.0): DockerHub/Quay vs GHCR​

GitHub Container Registry (GHCR) uses a different model: an artifact entity represents a package containing multiple versions (artifact.go). Verified.

Goals and non-goals​

Goals​

  • Define how OCI repositories, tags, manifests, and indexes should be represented.
  • Establish a stable upstream_id for each entity type.
  • Define how tag movement affects entity identity and evaluation history.
  • Compare the proposed models against concrete policy scenarios before implementation.
  • Describe how registry push events and GitHub package events map to the selected model.
  • Identify migration requirements for existing entity data.

Repository entities and webhook support are planned as a subsequent milestone under #6436.

The entity model needs to support the following policies:

  1. Every image in a repository must be signed
  2. latest must always be signed
  3. Tags other than latest must not change resolution
  4. Images must support amd64 and arm64
  5. Every tagged image has an SBOM

Non-goals​

  • Fixing all implementation bugs. This design targets systemic issues, not every bug; known bugs are tracked in the appendix findings table or in separate issues.
  • Implementing registry authentication. It may be necessary, particularly given DockerHub rate limiting, but is not part of this design.
  • Implementing specific policies for OCI registries in the Minder codebase. The primitives in this design should let the Rego and jq evaluators express policies such as image signing without hard-coding evaluation logic.
  • Adding support for new registries such as Harbor, ECR, GAR, or ACR.
  • Other distribution channels (GitHub Releases, PyPI, npm, etc.). See Does this generalize beyond OCI?.

Design: one entity per tag, identified by repo:tag​

Each artifact entity represents a repository and a tag. Today its upstream_id is repo@digest; this design redefines it as repo:tag. When compared with the alternatives considered, this design is referred to as Option A.

Both entities can point to the same digest, but each is evaluated independently.

A tag move is a manifest PUT that overwrites the tag pointer, so the tag name itself is the stable identity. The digest the tag currently resolves to becomes a property (oci/digest) rather than part of the identity. This resolves the mutable upstream_id described in the problem statement. DockerHub and Google Artifact Registry appear not to allow renaming repositories, so a name-based identity is not affected by server-side renames. Unverified.

Registration rejects container artifacts without an explicit tag, so every identity names its tag. See artifact_validator.go. Verified.

Entityupstream_idMulti-platform behaviour
Artifact (repo:tag)repo:tag, which stays the same when the tag moves. The current target digest is stored in oci/digest.The index digest is used as the version's Sha. Platform manifests remain inside the raw index passed to Rego. See oci.go.

When latest moves, its entity keeps the same upstream_id; only oci/digest changes. Whether GHCR converges on this model is open (see Future work).

Advantages​

  • Requires the fewest conceptual changes to the existing model.
  • Keeps tag-based policy selection straightforward.
  • Gives each tag a stable identity, so tag-move history can be attached to one entity (see Future work).
  • Avoids cross-entity reconciliation. A push combined with a tag move can produce N+1 manifests and a tag update in one burst of events; with separate Tag and Manifest entities this requires reconciling several entity types, while this design does not.
  • Avoids cross-entity result lookup (see Alternatives considered).

Observations and limitations​

  • Each tag is evaluated independently. This is sometimes desired (different policies can legitimately apply per tag, even on the same digest) and sometimes duplicate work, depending on the rule.
  • Untagged manifests are not discovered. The OCI distribution spec has no way to enumerate untagged digests, so this can't be supported generically. Unverified.
  • Tag movement is recorded through oci/digest and evaluation history rather than as an explicit entity transition.
  • Content-level policies remain dependent on tag-based discovery.

Event-handling principle​

An event is a prompt to re-check the current state at the source, not a payload to trust or apply in order. Events may be duplicated, dropped, or delivered out of order, and correctness does not rely on ordered, reliable delivery. When an event arrives, Minder re-reads the current state from the registry rather than applying the event's contents.

The oci ingest type​

DockerHub and Quay rules use a new ingest type, oci, instead of artifact. GHCR keeps using artifact until its entities become tags (see Future work).

OCI tag (oci)

Entity types: artifact (DockerHub and Quay)

Arguments:

message OCIType {
  // Artifact types of referrers to fetch for the tag's top-level digest,
  // for example "application/spdx+json". Empty means the referrers API
  // is not called.
  repeated string referrer_types = 1;
}

Data content: a JSON object with these fields:

  • digest: the digest the tag resolves to at evaluation time.
  • manifest: the top-level manifest, either an image manifest or an index.
  • manifests: the manifests the tag covers. For an index, every manifest it lists, with its platform. For a single image, a one-item list containing the image manifest itself, so rules don't need to branch on index vs image.
  • refs: for each requested referrer type, the referrer's descriptor and manifest.
  • verification: the sigstore verification results for the top-level digest, as a list with one entry per result, matching today's output. Verify returns one result per sigstore bundle, or a single unsigned result (container.go#L140-L151), and the artifact ingester emits one entry per result (artifact.go#L240-L277), so one digest can produce several verification entries. Verified.

Example for a tag pointing at a multi-platform index built with docker buildx:

{
  "digest": "sha256:1111...",
  "manifest": { "mediaType": "application/vnd.oci.image.index.v1+json", "manifests": ["..."] },
  "manifests": [
    { "digest": "sha256:2222...", "platform": { "os": "linux", "architecture": "amd64" }, "manifest": {} },
    { "digest": "sha256:3333...", "platform": { "os": "linux", "architecture": "arm64" }, "manifest": {} },
    { "digest": "sha256:4444...", "platform": { "os": "unknown", "architecture": "unknown" }, "manifest": {} }
  ],
  "refs": [
    { "artifactType": "application/spdx+json", "digest": "sha256:5555...", "manifest": {} }
  ],
  "verification": [
    { "is_signed": true, "is_verified": true }
  ]
}

How this differs from the artifact ingest type today:

  • Scoped to the entity's tag. The artifact ingester lists every tag in the repository and filters afterwards (oci.go#L215, oci.go#L287-L295). Verified. Fixing that is tracked in #7089.
  • Digest resolved at evaluation time. The oci/digest property is only as fresh as the last refresh. Inferred. The ingester therefore resolves the tag itself and records that digest in the evaluation checkpoint.
  • Manifests passed through as-is. docker buildx stores SBOM and provenance attestations as manifests inside the index, with platform unknown/unknown (Docker docs). Verified. These show up in manifests, not refs, and rule authors filter them out or use them as needed.
  • Referrers for the top-level digest only. Referrers attached to individual platform manifests aren't fetched. Whether they're needed is part of the signature-scope open question.
  • Signatures through both paths. Today's signature check looks up cosign's .sig tag (container.go#L409-L444). Verified. The referrers fallback in go-containerregistry looks for a sha256-<hex> tag instead, so refs alone would miss .sig-style signatures. Inferred. Keeping verification means existing signing rules carry over, while referrer-style signatures are reachable through refs.
  • Referrer manifests only, not blobs. SBOM documents can be large; fetching blob contents is left for later.
  • Caching by digest. Artifact ingestion uses a no-op ingest cache today (executor.go#L108-L112). The ingest cache key hashes the ingester config, which includes referrer_types (ingestcache.go#L80-L89), so two rule types asking for different referrer types already get different cache entries and never share a fetch. Verified. The oci ingester caches registry responses by digest within an evaluation, so manifest fetches are shared regardless of parameters.

SBOMs​

An SBOM is attached to a manifest through the referrers API, so "tag v3 has an SBOM" means "the manifest that v3 points to is referred to by an SBOM manifest". There are two possible configurations: one SBOM referring to the index, or one SBOM per platform manifest.

  • Leaning, not yet final: ingestion calls the referrers API, driven by per-rule-type parameters (for example, only fetch referrers of a given MIME type), so results can be cached and shared across rules on the same entity. Lazy fetching from Rego was set aside because each rule type runs in a separate Rego instance with no shared cache.
  • Still open: Whether to support one SBOM for the whole multi-platform index, one SBOM per platform manifest, or both. The ingestion approach above does not answer this.

Registry request cost​

Back-of-the-envelope numbers for one representative setup. These are inferred from reading the code, not measured.

Assumptions: a repository with 30 tags pointing at 15 digests (about two tags per digest), all 30 tags registered as entities, five rules (the policies listed in Goals), N = 2 platforms per image, and R = 1 referrer type of interest (SBOM). Signature checks go through verification, not refs, because .sig-style signatures aren't visible through referrers.

Each tag needs one resolve request to learn its digest, which can't be shared even when two tags point at the same digest, since they aren't known to match until both are resolved. That same request also fetches the tag's top-level manifest, because remote.Get returns the manifest when it resolves the tag (oci.go#L174-L182). Verified. The remaining work per digest is N platform-manifest fetches, one referrers call, R referrer-manifest fetches and two requests for verification (remote.Get plus the .sig manifest, container.go#L409-L444): N + 1 + R + 2 = N + R + 3 = 6 requests. With two tags per digest, that's 1 + 0.5 × 6 = 4 requests per tag at best. (Inferred.)

Two things can move these numbers:

  • If a registry doesn't support the OCI referrers API, go-containerregistry falls back to a sha256-<hex> tag, adding about one request per digest (remote/referrers.go). Verified for go-containerregistry v0.22.1; whether DockerHub or Quay need the fallback is Unverified.
  • Auth token handshakes are not counted.

Security considerations​

An asynchronous webhook-based system can detect and report that a tag now points to unsigned content, but it cannot guarantee that the tag never briefly points to such content. This is why latest "must always be signed" (policy 2) can be detected but not guaranteed. Preventing publication of unsigned content would require an enforcement mechanism beyond post-publication evaluation.

Future work​

Tag history​

The main identity question is what remains stable when a tag changes its target.

Stable upstream_idBehaviour when a tag moves
Stable: repo:tag (redefined; see Design). Today it is repo@digest, which follows the tag's current target.The entity, its upstream_id, and its history row stay the same; only oci/digest changes. Today, the upstream_id is updated during a subsequent non-stale refresh, such as a profile change or GetArtifactById call. See refresh_by_id.go. Historical results do not identify the digest that was evaluated.

Tracking the history of tag → digest resolution is useful under this design. For example, asserting something like 'v4 has been signed for the last year' even as v4 moves across different manifests over that time.

TOFU storage for policy 3​

Without a way for rule types to read previous evaluation state, policy 3 (immutable tags) can't be implemented today.

Tag movement is detected through comparison with previously persisted state; neither a property-change trigger nor persisted state exists today. Persisted state gives a comprehensible history but can miss intermediate states, for example when latest is moved to the wrong digest and then corrected, or during a release. This trade-off is accepted rather than treated as solved.

Artifact webhooks and reminder coverage​

Existing event payloads​

  • DockerHub push: Includes push_data.tag, pusher, pushed_at, and repository information. The documented payload does not include the digest or a delete event. See the Docker Hub webhook documentation, fetched 2026-10-25.
  • Quay Repository Push: Includes repository and namespace information, docker_url, and updated_tags[]. The cited notification guide does not establish a digest or delete event in the payload. See the Quay notification guide. Newer Red Hat documentation remains unverified.
  • GitHub package event: The current handler processes only published. The payload struct includes package_version.container_metadata.tag.{name,digest}, but the values are not currently used. Whether GitHub reliably populates the digest field remains unverified. See handlers_packages.go.

In summary, all three sources (DockerHub, Quay, and GHCR) reliably provide a tag name in push payloads; none reliably provides the digest of the pushed content. Every option therefore needs an extra request to resolve the digest.

Deletion detection and drift correction require a reconciliation mechanism that compares stored state with registry state. The existing reminder service covers repositories only.

Push events alone do not guarantee complete discovery. In particular, an event that names a tag is not equivalent to an event that identifies every manifest in a repository.

Reconciliation: Periodic reconciliation should be integrated into Reminder, which currently covers repositories only. A small follow-up issue should extend Reminder to cover artifact entities (and eventually all entity types). Run frequency still needs to respect registry rate limits.

Registry constraints. Push and tag-ordering constraints vary by registry: ECR requires a repository to exist before it is pushed to, while other registries create it automatically. This is one more thing Minder can observe but not enforce.

If tags are registered automatically in the future, their originated_from would point at the entity that caused the registration, probably the OCI repository.

GHCR entities as tags​

Does GHCR expose platform manifests as separate untagged versions? This remains unverified; see #6829. GHCR also has quirks that may justify a custom implementation track rather than assuming full convergence on the same timeline as DockerHub and Quay: GitHub App tokens do not work for GHCR authentication, and GHCR likely tracks organization renames differently from DockerHub.

Recording the evaluated digest in the checkpoint​

Recording the evaluated digest in the checkpoint's existing Digest field could make tag history auditable; the field is currently unused by the artifact ingester. See checkpoints.go. Tracked in #7089.

  • Surface the evaluated digest. Recording the digest in the checkpoint's Digest field only helps if it is surfaced. ListEvaluationResultsHistory does not currently return the checkpoint. This is a follow-up requirement, not only a storage change.
  • Extend EvaluationHistory. Once the checkpoint gap above is addressed, consider extending the EvaluationHistory message to carry the evaluated digest or tag target directly. This would record the evaluated digest and a timestamp, not the full property set, since properties can drift after the evaluation.

Alternatives considered​

Keeping repo@digest​

Keeping today's repo@digest identity was considered. It was not chosen because the identity changes whenever the tag moves, which defeats the purpose of upstream_id as a durable identifier.

Option B: Introduce separate Tag and Manifest entities​

Under this model, a Tag represents a mutable reference, while a Manifest represents immutable content. Multiple Tags can point to the same Manifest, and a Manifest can exist without any Tags.

Entity-at-a-time evaluation may not work cleanly with nested objects: a manifest can be either an index (manifest list) or an individual manifest, which can make rules harder to write. This is part of why Option B's cross-entity lookup risk matters.

Candidate identities​

EntityCandidate upstream_idNotes
Tagrepo:tagRegistries do not expose a separate tag ID, so the repository and tag name form the identity. Deleting and recreating the same tag would reuse that identity. The current target digest could be stored in a property such as oci/digest.
Manifestrepo@digest for DockerHub and Quay. For GHCR, either a package version ID or repo@digest remains under consideration.The digest identifies immutable content. Including the repository keeps copies of the same digest in different repositories distinct, addressing the identity concern raised in #6808.
Platform manifestB1: Keep platform manifests as data inside the index Manifest. B2: Represent each platform manifest as its own repo@digest entity.B2 requires a relationship between an index and its child manifests. A child may be referenced by multiple indexes.

A tag and a platform manifest could also both point directly at the same child manifest inside an index, for example a linux/amd64-only tag pointing at a manifest that is also a platform manifest of an index. This is an unresolved modeling question for B2 if B is revisited; it does not block the A direction.

Advantages of Option B​

  • Separates mutable references from immutable content.
  • Provides a natural place for tag-specific policies and tag-movement history.
  • Allows content-level checks to be associated with a digest rather than repeated for every tag.
  • Provides a model for manifests that exist without tags, provided they can be discovered.

Limitations of Option B​

  • Requires explicit lifecycle handling for Tags and Manifests.
  • Requires a mechanism to detect changes to a Tag's target digest.
  • Reusing Manifest evaluation results from Tag rules requires additional cross-entity lookup or equivalent functionality.
  • B2 introduces relationships that the current originated_from model cannot represent.

If a Tag's policy depends on a Manifest's result, evaluation order between the two would matter, and Minder has no mechanism for event ordering today (see Design > Event-handling principle), so correctness would depend on re-checking state rather than trusting arrival order.

originated_from is ON DELETE CASCADE and models lifecycle ownership: when a parent is deleted, the entities that originated from it are cleaned up. Tag → Manifest is not ownership. It is a point-in-time reference that changes without either side being deleted, so cascading a delete through it would be wrong. Given the move to Option A this may be moot, and it is low priority to resolve further.

Why Option B was set aside​

Option B was this document's original recommendation. It was set aside because of cross-entity lookup: a Tag rule either duplicates the Manifest's content check, which gives no real improvement over A, or needs to look up the Manifest's evaluation result. Cross-entity result lookup does not exist today and is risky to build.

Option C: Introduce Manifest entities only, with tags stored as data​

This model does not introduce separate Tag entities. Instead, tag information is maintained either on the Manifest or on a Repository entity.

Two variants are possible:

  • C1: A Manifest stores its current tags in a property such as oci/tags.
  • C2: A Repository stores a mapping from tag names to digests.
EntityCandidate upstream_idNotes
Manifestrepo@digestSame identity approach as Option B.
TagsNo separate entityWhen a tag moves, the old Manifest loses the tag and the new Manifest gains it under C1. Under C2, the corresponding Repository mapping is updated.
Platform manifestSame B1/B2 decision as Option B.

Advantages of Option C​

  • Keeps the entity model smaller.
  • Supports content-level evaluation and digest-based deduplication.
  • C2 can centralise tag state and potentially simplify repository-level policies.

Limitations of Option C​

  • Tag movement is not naturally represented as a first-class entity transition.
  • C1 requires updating tag information on the affected Manifests.
  • C2 requires Repository-level state and policy support.
  • Historical tag movement still requires persisted previous state or an equivalent event history.

Why Option C was set aside​

C1 is retired from serious consideration. The entity model has no precedent for set-style properties, and during a race the same tag could appear in two Manifest entities' property lists. C2 is set aside alongside C1.

What the scenarios tell us​

Options B and C provide a clearer model for content-level checks and can avoid repeated evaluation of the same digest. However, deduplication depends on rule configuration and evaluation semantics; it is not guaranteed merely by creating Manifest entities.

Option B gives mutable references a first-class identity, which makes tag-specific policies and movement tracking easier to express.

Redefining Option A's upstream_id as repo:tag also gives each tag a stable identity, without B's cross-entity lookup.

Alerting when a tag moves to a new digest still requires previous-state tracking or an equivalent change-detection mechanism regardless of the selected entity model.

Detailed comparison of Options B and C​

Scenario notes by option​

These notes come from the earlier scenario table. The A notes describe today's behaviour; redefining A's upstream_id changes identity, not discovery.

  1. (a) Every image under platform/supported/ must be signed.
    • A: Each repo:tag must be registered manually. Selection can use oci/repository (#6929). Each registered entity may re-check every tag in the repository. New pushes are not automatically discovered.
    • B: Manifest rules can select by oci/repository and evaluate each discovered digest. Complete coverage depends on repository enumeration, push-event processing, and reconciliation.
    • C: Same content-level model as B. Complete coverage depends on discovery and reconciliation.
  2. (b) latest must never point to an unsigned manifest.
    • A: A rule can filter with tags: [latest], but a tag move is not automatically detected or evaluated.
    • B: A rule can select the Tag named latest and evaluate its current target digest. Push processing and reconciliation determine how quickly a change is observed.
    • C: C1 can select Manifests whose current tags include latest; C2 can evaluate the Repository's tag map. Both require tag-state updates and evaluation triggers.
  3. (c) Alert when a tag moves to a new digest.
    • A: A change to upstream_id is not recorded as an explicit movement event. The history does not retain the evaluated digest.
    • B: Compare the Tag's previously observed digest with the newly resolved digest. A property-change trigger or persisted prior state is required; neither exists today.
    • C: Requires previous and current tag state, either through the Repository map (C2) or equivalent persisted information.
  4. (d) Every image must support amd64 and arm64.
    • A: Possible through the raw index, but the same content may be checked once per tag. An index without linux/amd64 may also break version listing.
    • B: Under B1, evaluate the index's platform descriptors once per digest. Under B2, platform manifests can be evaluated independently.
    • C: Same content-level approach as B, with the same B1/B2 choice.
  5. (e) One digest has three tags: how many evaluations occur?
    • A: Three registered entities may each evaluate the same digest. Estimated: three status rows and nine verifications, depending on the evaluation path. Inferred.
    • B: Manifest-level rules can evaluate the digest once per evaluation cycle; Tag-level rules remain per Tag. Cross-entity reuse is not automatic.
    • C: Manifest-level rules can evaluate the digest once per evaluation cycle.
  6. (f) An image is pushed by digest without a tag.
    • A: Not discovered by the current tag-based model.
    • B: Can represent a Manifest without Tags if its digest is discovered through another mechanism. Existing push payloads do not provide sufficient information to guarantee discovery of every untagged Manifest.
    • C: Same limitation as B.
  7. (g) Every tagged image has an SBOM.
    • A, B, and C: Same ingestion approach (see The oci ingest type).

The OCI distribution spec's Deleting Manifests section states that once a manifest is deleted, "any tag pointing to that digest will return a 404". Deleting a tag does not delete the manifest. If Tag and Manifest entities are introduced (Option B), deletion can be handled by deleting both entities directly rather than routing it through originated_from. Expected cost under B and C​

  • A Manifest evaluation is expected to require roughly three GET requests in the described path: one for the raw manifest and two for signature lookup.
  • A Tag evaluation adds a digest-resolution request. This might be implemented with a HEAD request on Docker Hub, although #6862 retained GET for consistency.
  • Event-driven evaluation could reduce repeated repository-wide scans, provided reconciliation and recovery from missed events remain available.

These estimates should be validated through request-level measurements before being used as implementation guarantees.

Retention​

Which retention or aging-out policy determines when Manifests should be removed? Under B and C, the number of Manifest entities grows with every push. See the #6779 discussion. It is unresolved how registries handle garbage collection themselves. This is another point in A's favour: A does not accumulate a growing set of Manifest entities the way B and C do. Descoped, tracked separately. Discussed on the 2026-10-30 design call and scoped out of this design. What happens to evaluation history when an entity is deleted is a general problem for every entity type, not one specific to OCI. Evan is filing it as a separate design issue.

Does this generalize beyond OCI?​

This question was raised by @intelligent-ears on #6954: at the Oct 22 community meeting, maintainers noted that release-style entities (e.g. npm, PyPI) have a similar gap, and Evan sketched a hierarchy along the lines of Account → Distribution channel → Release → Artifact. That hierarchy comes from the Oct 22, 2026 community meeting notes: ‘Evan came up with a quick set of possible entities around releases: Account (admin group within the distribution), Distribution channel (npm package, pypi package), Release (specific version), Artifact (component in that release, e.g. platform-specific binary).’ Verified.

npm has a concept that maps closely onto Tag and Manifest:

  • A dist-tag (e.g. latest, beta) is "a human-readable label... used to provide an alias instead of version numbers" (npm docs, npm dist-tag). Verified. A dist-tag maps to a single version, and latest moves to the newest version on every default npm publish. Verified. Any dist-tag, including latest, can be repointed with npm dist-tag add; the docs don't say outright that this replaces an existing mapping, but that follows directly from "maps to a single version." Inferred.
  • A published name@version can never be republished or reused, even after npm unpublish removes it (subject to npm's unpublish policy). Its content is identified by a hash: dist.integrity (SHA-512) and the legacy shasum (SHA-1). Verified. npm deprecate is a reversible warning flag and does not touch the content. Inferred.
  • A single version can carry more than one dist-tag at once: checking the live registry shows the npm package itself has both latest and next-12 dist-tags pointing at the same version, 12.2.1. Verified (observed directly, not stated in docs).

This maps onto the design the same way OCI does: dist-tag ≈ Tag (mutable, name-addressed, points to one target at a time, though a target can have several names), and version ≈ Manifest (immutable, content-addressed, can exist with zero or more tags pointing to it).

PyPI does not have an equivalent. There is no tag concept; files are grouped under each version, and each file carries a sha256 and other hashes with a filename that can never be reused. Verified. Yanking a release hides it without deleting it, and can be undone. Verified. One caveat: PyPI files are fetched by filename and carry hashes for verification, not fetched by hash the way OCI blobs are, so calling them "content-addressed" in the same sense as a Manifest digest may overstate it. Whether new files can be added to an existing version after release remains unverified.

So the split doesn't generalize uniformly: it matches a registry that has a movable, name-based alias (npm, OCI) but has no direct counterpart where there's no such alias (PyPI, as checked here). That's consistent with treating Tag as "the mutable pointer a particular ecosystem happens to expose," rather than a feature every ecosystem must have.

Follow-up pointer (later, not current scope): Maven Central and crates.io were raised in review as other registries to compare. Their models have not been analyzed yet; that is later work.

Design call notes (2026-10-30)​

Discussed on the 2026-10-30 design call.

  • Lazy fetching from Rego: set aside. Each rule type runs in a separate Rego instance with no shared cache, so deferring registry fetches (such as referrers) to Rego could cause more registry requests, not fewer, when several rules evaluate the same entity.
  • Leaning: ingestion-time, per-rule-type parameters. A rule type declares what it needs at ingestion time, for example "only fetch referrers of a given MIME type". Ingestion can then cache those results and share them across all rules evaluating the same entity.

Open design TODOs from the call:

  • (a) Add parameters to OCI ingestion so each rule type can specify which referrer types to fetch.
  • (b) Possibly change the ingestion shape for OCI repositories, and consider a new ingest type (for example oci) separate from GHCR's existing artifact ingest type, with GHCR migrating to it over time.

Both are done: (a) is the referrer_types argument and (b) is the new oci ingest type, both described in The oci ingest type.

Earlier cost notes​

Cost multipliers​

  • Artifact ingestion is not cached, so each artifact rule repeats the ingestion work. See executor.go.
  • Registering multiple tags from the same repository can repeat repository-wide processing.

Mitigations and action items​

  • Caching layer. A caching layer can be added if Minder hits registry limits (notably DockerHub) or if ingestion is simply expensive. The cache is keyed by digest: each tag is first resolved to its digest, and the manifest and signature lookups are then cached by that digest. Because several tags that share a digest resolve to the same cache key, the content work is done once per digest rather than once per tag, without needing Manifest entities, which supports one entity per tag.
  • Metrics. Add OpenTelemetry meters for registry call volume, and possibly the credentials used, reusing what exists for the GitHub provider where possible.

Rate limits​

Docker Hub documents limits of 100 pulls per six hours per IP for anonymous users and 200 for authenticated personal accounts. Manifest GET requests count toward these limits; HEAD requests do not. See the Docker Hub usage and pull limits documentation, fetched 2026-10-25.

The current OCI listing and manifest calls do not provide credentials in the cited code paths. See oci.go, oci.go, and oci.go. The resulting impact on anonymous rate limits is inferred.

For example, a repository with 20 tags inside the retention window may require approximately 100–120 manifest GETs for one rule. This is an estimate, not a measured result.

Quay's applicable limits remain unverified.
